# Real container verification checklist

Written 2026-11-19 for the read-only review in 08-roadmap-status.md. That file says none of the recent changes was run against a real Nest container: container behaviour is covered by tests against a mock SSH server with stand-in `systemctl` and `journalctl`. This checklist is the work a person with a real Nest container can do to close that gap. Run it in order, record what actually happened, and write the results into `docs/selfhost/README.md`.

Run the shell commands below inside the Nest container over SSH. Egg stores a root key for the container, so `systemctl`, `journalctl`, `docker` and `cat /etc/systemd/system/...` are available without `sudo`. Replace `<slug>` with the project slug shown in the URL, and `<8hex>` with the first eight characters of a release id from the deployment log.

Status note (checked 2026-11-22): the two areas that were "being implemented" when this checklist was written are now **built but not verified on a real container**. The Dockerfile/Compose deployment modes (`web/src/server/deploy/docker-target.ts`, `deploymentMode` on projects, capability-gated pickers in `components/hosting-options.tsx`) and the worker's optional listen port (`listenPort` in `server/db/schema.ts`, the Settings field and the process-state health model) are in the code. This is still a verification checklist, not a record of passed tests: run sections 5 and 6 and record what actually happened. The quoted strings come from the components and may have changed; record any difference as a finding.

App pages used here: the global Projects, Deployments, Domains, Container and Account pages, and the project tabs Overview, Deployments, Analytics, Files, Terminal, Team and Settings.

## 1. Native web deployment, the known baseline

1. On the New project page, create a Node.js web service and deploy it. On the deployment page, watch the Timeline panel. Expect the stages in this order: Queued, Preparing, Building, Starting, Health check, Live. A project with no build step shows Building as skipped. Expect the Health check detail to read "Waiting for the app to answer on port <port>" and the Live note to mention uptime checks and the Logs tab.
2. Open the "Build Logs" panel while the deployment runs. Expect it to stream lines, show a line count, accept "Find in logs" and end with a success or failure mark. Confirm a failed deploy leads with "This deployment failed" and one sentence saying what to fix.
3. Confirm the app answers on its port on the container: `curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:<port>/`. Expect a 2xx, 3xx or 4xx answer, which is what the pipeline's health check accepts. Confirm the unit reads PORT and HOST 0.0.0.0 with `cat /etc/systemd/system/egg-<slug>.service`.
4. On the Deployments page, use the actions menu on an older production deployment. Expect "Redeploy" on every ready deployment and "Instant rollback" only on a production deployment that is ready, is not current and has not been cleaned up. Run "Instant rollback" and expect the Timeline to show Queued, Switching release, Health check, Live, and the log to end with "Rollback complete. Database changes are not reversed."
5. On the Domains page, add a domain with the app's target port and press "Add domain". For a custom domain expect the "Next: finish setup for <domain>" block with the CNAME and TXT records, the sentence "At your DNS provider, add a CNAME record for ... pointing to:" and the instruction to add the domain on the Domains page of the Nest dashboard with that target port and press Check. Expect the row to read "Waiting for DNS" until the record resolves, then "Active". Press "Check" and expect either an "App check" answer from the running app or "Needs attention" with "DNS no longer points here. Check your record."

## 2. Worker and bot path

1. On the New project page, set Workload to "Bot or background worker". Expect the help text: "For bots and background apps, such as a Discord bot, a Slack app or a queue worker. No HTTP health check: Egg keeps the process running under systemd and checks that it stays up." Expect the port field to be hidden at creation and the workload to be locked to that project afterwards. Deploy a Node.js worker and a Python worker.
2. On the deployment page Timeline, expect the health stage to be labelled "Process check" and its detail to read "Checking that the worker stays active", not a port wait. The log should contain "Worker is active" and end with "Worker is running." A worker that does not stay active should fail with "The worker did not stay active. Check its logs and start command."
3. On the container, read `cat /etc/systemd/system/egg-<slug>.service`. Expect `Restart=always`, `RestartSec=3`, `OOMScoreAdjust=-500`, and no `Environment=PORT` line. Check `systemctl is-active egg-<slug>.service` returns `active`.
4. On the project Overview page, open the "Worker process" card. Expect four readings: Status, Uptime, Memory and Restarts, with no Health check reading. Expect "Check now" to re-read the container and "Restart" to ask for confirmation before restarting. Confirm "Checked <time>" and the note that readings are reused for 30 seconds.
5. Wait through two monitor passes, which run every few minutes. Confirm the uptime state stays green while the process stays active. Confirm the status page, if published, says the worker is running.

## 3. Crash and restart behaviour

1. Kill the process once with `systemctl restart egg-<slug>.service` inside the container. Expect systemd to bring it back within a few seconds. On the Worker process card, expect Restarts to climb by one and Uptime to restart from zero. Confirm with `systemctl show egg-<slug>.service -p NRestarts --value`.
2. Make the app crash on start, for example by deploying a start command that exits immediately. Expect systemd to restart-loop it. Confirm on the container with `systemctl show egg-<slug>.service -p NRestarts -p ActiveState` and `journalctl -u egg-<slug>.service -n 50 --no-pager`. Expect the Worker process card to show Status as "Crashed" or "Starting" and a rising Restarts count.
3. Expect the monitor to open a down alert only after two failed checks. The alert title should say "<project> has stopped", and the detail should say the process keeps failing to start, keeps restarting, is stopped, is not on the container any more, or is not running. Expect one recovery alert with the title "<project> is back up" when the process comes back, and no repeat message while it stays up.
4. Drive an out-of-memory kill during a build. On the Container page, set "Build memory" low enough that the build cannot finish, then deploy a build that allocates memory. Expect the log line "Building on your container, capped at <n> MB of memory" and the failure "The build needed more memory than the cap of <n> MB. Your app is still running." Check the scope with `systemctl show egg-build-<8hex>.scope -p MemoryMax -p MemorySwapMax` while it runs. Expect a real MemoryMax with no swap.
5. Confirm the priority order. On the container, expect the build scope to carry `OOMScoreAdjust` equivalent to 500 from its launch, and the app unit to carry `OOMScoreAdjust=-500`. When the kernel kills the build, expect the running app and its release folder to be untouched.

## 4. Scheduled jobs

1. On the project Settings page, open the "Scheduled Jobs" card. Confirm the description says "Run a command on a schedule inside your latest release, such as a nightly clean-up or a weekly report. Times are UTC." Add a job with a preset such as "Every 15 minutes" and a command that prints a line. Expect the message "Added. It is armed on your container now."
2. Check the schedule preview before saving. Expect text such as "Every day at 03:00 UTC, next <YYYY-MM-DD HH:MM> UTC". This is the dashboard's reading of the timer. On the container, confirm the real timer with `systemctl list-timers 'egg-<slug>-job-*'` and `cat /etc/systemd/system/egg-<slug>-job-<8hex>.timer`. Expect an `OnCalendar` line ending in `UTC`, `Persistent=false`, `AccuracySec=10s`, and the matching `egg-<slug>-job-<8hex>.service` unit with `TimeoutStartSec=1800` and `OOMScoreAdjust=500`.
3. Wait for one timer fire. Expect the job row to show "Succeeded <time>" or "Failed (exit <n>) <time>". Press "Run now" and expect "Started <name>. Open its output to see what it printed."
4. Press the output button and expect the printed lines under "Output of <name>". Press "Pause" and expect the row to show "Paused" and "Next run" to disappear. Confirm on the container that the timer is disabled with `systemctl is-active egg-<slug>-job-<8hex>.timer`. Press "Resume" and expect it armed again.
5. Check the caps. Add a sixth job and expect the refusal "A project can have 5 jobs. Remove one to add another." Set a command that sleeps longer than 30 minutes and confirm systemd stops it at `TimeoutStartSec`. Set a cron expression more often than once every five minutes and confirm the timer does not fire more often than that limit. Remove the test jobs and confirm both unit files are gone from `/etc/systemd/system`.

## 5. Worker with an optional URL (built, unverified on a real container)

1. On the Settings page of a worker, find "Listen port (optional)". Expect the help text: "Fill this only if the bot must receive webhooks over HTTP. A domain can point at it once it is set. Leave it empty to keep the worker closed." Confirm a portless worker keeps no listener and no domain option.
2. Set a listen port, redeploy, and confirm the process actually listens on it inside the container with `ss -ltnp | grep <port>` or the equivalent. Add a domain for that port on the Domains page and let Caddy route it. Expect the row to become "Active" after the DNS check.
3. Send a Slack-style request to the request URL, for example `curl -X POST https://<domain>/<path> -d '{"type":"url_verification","challenge":"test"}'`. Expect the worker to log the request in `journalctl -u egg-<slug>.service` and, for a verification challenge, to answer with the challenge.
4. Confirm the health model did not change. The Timeline should still show "Process check" with "Checking that the worker stays active", no "Health check" row and no health path. Stop the HTTP listener inside the worker while leaving the process alive and confirm Egg still treats it as up; then stop the process and confirm the down alert after two failed checks.
5. If the field, the routing or the wording differs from this description, record the honest state rather than marking the item passed. The product claim is only that a worker may expose one port and keep process-state health checks.

## 6. Docker deployment modes (built, capability gated, unverified on a real container)

1. Connect or retest the server, then open the Workload and Deployment mode pickers on the New project page. Expect "Native process · systemd", "Dockerfile" and "Docker Compose". Expect Dockerfile and Docker Compose to be disabled with the " · unavailable" suffix when the capability probe does not enable them. Expect the mode help: "Container builds require a working target Docker engine, resource limits, disk capacity and verified port mapping. Persistent data needs explicit volumes."
2. Check the probe result and its reason. With no Docker engine, expect the reason "Docker engine is unavailable or inaccessible on the target. Cgroup limits, disk capacity and port mapping are unverified." followed by " Compose CLI is unavailable." or " Compose CLI is present.". With an engine but unimplemented limits, expect "Docker engine responded, but cgroup limits, disk capacity and port mapping are unverified; Docker deployment is not yet implemented." With an invalid probe answer, expect "Target capability probe returned an incomplete or invalid response." With no probe at all, expect "Docker target support has not been verified. Test the server connection before choosing a container mode."
3. If Docker is unavailable in the LXC, confirm the mode is refused with that exact reason rather than accepted and then failing at deploy time. Record the reason string. Do not report the Docker path as passing.
4. If the modes are enabled, create a Dockerfile project with "Dockerfile path" set to "Dockerfile". For a web workload set "Internal container port" to the port the image listens on. Expect a build on the container and an image in `docker images`. Read `cat /etc/systemd/system/egg-<slug>.service` and expect the unit ExecStart to run `docker start -a` for the release container, with `Restart=always` and the memory cap mapped onto the container. Confirm `docker ps` shows the container running.
5. For a Compose project, set "Compose file path" to "compose.yaml" and "Compose service" to "app". Expect the selected service to be the one started and monitored, and the other services in the file to be left alone.
6. Kill the container with `docker kill <container>` and expect systemd to bring it back. Expect the Worker process or Service card Restarts to climb and a down alert if it stays down for two checks. Confirm the port mapping for a web workload from the outside: the mapped host port should answer the app, and the domain pointing at that port should work.
7. Deploy a second release, then use "Instant rollback" on the first one. Expect the previous image to be started again and the health or process check to pass. Confirm with `docker ps` that the running container is the older release image.
8. Delete the project through the Delete Project card. Expect its containers and images to be gone from `docker ps -a` and `docker images`, while any named volumes holding persistent data are kept as the card stated. Record anything the cleanup leaves behind with the exact name.

## 7. Alerts and notifications

1. On the project Settings page, open "Notifications". Paste a Discord or Slack incoming webhook URL, choose "Every deployment" or "Failures only" under "Send", and press "Save". Expect "Saved. Send a test message to check it." and a summary of the service and which deployments are sent. Press "Send test message" and expect "Sent. Check the channel." and a message headed "Test from Egg for <project>". Confirm other URL shapes are refused with "Only Discord and Slack incoming webhook URLs are supported."
2. Deploy successfully and expect "<project> is live in production" with the branch, short commit, commit message and duration. Deploy a failure and expect "<project> failed to deploy to production" with the recorded error. With "Failures only", expect no message for a successful deploy.
3. Crash the worker as in section 3 and expect "<project> has stopped" on the webhook, followed once by "<project> is back up". For a web project the down title is "<project> is not answering".
4. On the "Alerts" card, check the "Send to the webhook" choices. For a worker expect "The worker stops running" and "The worker runs again"; for a web service expect "The app stops answering" and "The app answers again". Expect the down channel after the configured failed checks, default 2, and one recovery message. Expect resource warnings to fire once at the limit and once when they clear.
5. Test mute. Choose "For 1 hour", "For 24 hours" or "Until I resume" under "Pause all alerts" and press "Pause". Expect "Alerts paused" and the warning "Alerts are paused" with "Events are still recorded.". Trigger a down alert and confirm the History row is marked "Not sent, paused" but still present. Press "Resume alerts" and expect "Alerts resumed" and messages to flow again.

## 8. Container housekeeping

1. Open the Container page. Expect the disk reading with "Read from the container at <time>", then the sections "Projects", "Orphans" and "Other ports". Expect "Projects" to list the units as `egg-<slug>.service` with a state label of Running, Starting, Crashed, Stopped or No service yet, and "Background worker" for a worker. Expect "Other ports" to show "This container only" or "Open to the network", or the note that neither `ss` nor `netstat` is available.
2. Press "Refresh" and expect "Reading…" followed by a new "Read from the container at <time>". Create and delete a project and confirm its service and folder stop appearing under Projects and do not appear under Orphans.
3. In Account, under Container permissions, confirm the switches "Terminal", "File changes" and "Removing leftovers" exist and start Off for a new server. Expect "The terminal is turned off for this server." and "File changes are turned off for this server." where the features are hidden. Turning Terminal or File changes on should ask for a fresh Hack Club sign-in and a typed confirmation of the server name. Confirm turning a switch off never restarts an app.
4. With Terminal on, open the project Terminal tab. Expect a shell that runs as root on the container and that `systemctl status egg-<slug>.service` works. With Terminal off, expect the off message and no shell.
5. With File changes on, open the project Files tab. Expect the shared folder to be writable and the `current/` live release to be read only with "current/ is the live release and is read only." Confirm a file written to `shared/` survives a redeploy. With File changes off, expect the off message and no write controls.
